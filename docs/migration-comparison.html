1.3 YAML 示例片段对比

旧 场景式（命令嵌在 markdown 中） 
scenarios:
- npu: Atlas 800I A2
  precision: W8A8
  deployment: 单节点-多卡
  steps:
  - title: Start the server
    content: |-
      ```bash
      export HCCL_BUFFSIZE=1024
      export OMP_PROC_BIND=false
      vllm serve your_model_path \
        --tensor-parallel-size 8 \
        --quantization ascend \
        --trust-remote-code \
        --enable-expert-parallel
      ```
新 结构化（程序可读） 
model:
  base_args:
    - "--trust-remote-code"
    - "--enable-expert-parallel"
  base_env:
    HCCL_BUFFSIZE: "1024"
    OMP_PROC_BIND: "false"

features:
  quantization_ascend:
    args: ["--quantization", "ascend"]

variants:
  default:
    precision: w8a8
    vram_minimum_gb: 31

hardware_overrides:
  ascend_a2:
    extra_args: ["--compilation-config",
      '{"cudagraph_mode":"FULL_DECODE_ONLY"}']

3. verify-recipe.sh 对比

这是整个迁移中改动最大的组件。旧脚本"提取 shell 命令直接执行"，新脚本"从结构化字段拼装命令"。

阶段旧逻辑新逻辑
1. 解析 YAML 读取 scenarios[]/verification/env_setup 字段 读取 model/features/variants/hardware_overrides
2. 命令生成 re.search(r'```bash\n(.*?)```', content) 正则提取 merge_args(base, features, variant, hw, smoke) 程序化拼接
3. 环境变量 嵌入 shell 代码块的 export 语句 merge_env(base_env, feat_env, var_env, hw_env) 分层合并，后覆盖前
4. 验证 curl 从 verification 字段的 ```bash 块提取 自动生成标准 /v1/chat/completions + /v1/models 请求
5. 场景遍历 for s in data.scenarios: for var_name, var in variants.items():（仅单选 single_node_tp 策略）
6. VRAM 检查 无 新增：vram_minimum_gb / TP > NPU 容量 × 0.85 → 跳过
7. 多节点 检测到 \$1/\$2 位置参数自动跳过 仅运行 single_node_tp，多节点 / PD 策略不生成 scenario
8. Pip 安装 从 env_setup.pip.content 提取并执行 不再需要（vllm-ascend 预装在 runner 镜像）
9. 冒烟默认值 跟随 scenario 中的命令（参数各不相同） 硬编码：TP=8, max-model-len=8192, max-num-seqs=4, gpu-memory-utilization=0.9
10. MoE 兜底 依赖 scenario 命令中已有的 --enable-expert-parallel 自动补充：is_moe and '--enable-expert-parallel' not in args → 插入
11. %%CONFIG%% 标记 re.sub(r'%%CONFIG:...%%', '', bash) 无需处理（新格式无此模板语法）
12. your_model_path bash_content.replace('your_model_path', CACHE_PATH) 直接传入拼装好的参数列表
⚠ 关键限制：新脚本只运行 single_node_tp 冒烟测试。PD 分离（Mooncake）、多节点 TP/EP、PD Hybrid 等复杂部署场景不再自动化验证，需在真实多节点环境中手动测试。

  • build-recipes-api.mjs：跳过 models/ 根目录下的非 recipe 文件
  • src/lib/recipes.js：跳过 parts.length < 2 的文件，filter(Boolean)
  • providers.js：THUDM logo 走 CSS fallback
  • 旧文件清理：删除 models_old_en/、models_old_zh/、src_astro/、public/生成物

7. 常见坑点

#坑点说明解决
1 YAML 转换不可全自动 旧 scenario 的 shell 代码块包含大量隐式知识（TP 大小、EP 开关、编译 flag），必须人工提取到结构化字段 逐个模型审查，确保 base_args/features/hardware_overrides 覆盖所有必需参数
2 VRAM 值不准确 vram_minimum_gb 是 CI 验证的准入条件，算错会导致真机测试被跳过或 OOM 按公式 params × bytes_per_param × 1.2 计算，对混合精度量化使用真实权重文件大小
3 冒烟参数对超大模型不适用 TP=8 + max-model-len=8192 对 GLM-5.2 (753B) 可能 OOM，每个 NPU 需装 ~94GB（>64GB A2 容量） 对于 vram_per_npu > 64G 的 variant，脚本自动跳过
4 _cache_paths.yaml 遗漏 新增模型不加条目 → CI 跳过（"未提前下载权重"） 每次新增模型同步更新此文件
5 features 默认开关搞反 不在 opt_in_features 的功能被视为默认开启，会拼入 serve 命令 确保默认开启的功能在所有目标硬件上都可用
6 hardware_overrides key 不匹配 脚本使用的 key 是 atlas_800_a2/atlas_800_a3，YAML 中必须一致 保持 key 名称与 RECIPE_HW_KEY 环境变量一致
7 basePath 不一致 next.config.mjs 的 basePath 必须与 providers.js 的 BASE_PATH 常量同步 改仓库名时两处一起改
8 models/ 根目录文件被误解析 _cache_paths.yaml 等文件被 YAML 扫描器误当作 recipe 加载 在 build-recipes-api.mjs 和 recipes.js 中均添加 parts.length < 2 → continue 保护
